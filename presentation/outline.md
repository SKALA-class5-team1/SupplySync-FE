# SupplySync 발표 구성안

> 교수님 평가 항목 순서를 따른다. `[확인]` 표시는 팀에서 수치나 사실을 확인해야 하는 부분이다.

## 0. 표지
- 제목: SupplySync, RFQ 견적 회신을 줄이는 AI 에이전트
- 한 줄: 사양 검토·재고 확인·승인이 순차로 밀리는 견적 회신 과정을 한 흐름으로 묶는다.

## 1. 문제와 아이템 (평가항목: Biz. 아이템)
- 문제: RFQ 견적 회신이 느리다. 원인은 사양 검토, 재고 확인, 승인이 부서별로 순차 진행되기 때문이다.
- Pain point: [확인] 검증한 출처(인터뷰, 업계 자료, 내부 데이터)와 수치를 적는다.
- 기존 서비스(CPQ 등)와의 차이
  - CPQ는 정해진 규칙으로 구성과 가격을 계산하는 데 강하다.
  - SupplySync는 고객 요청서 원문을 읽고, 빠진 값과 이상한 값을 찾고, 재고가 모자라면 대체 부품을 제안한다. 판단 근거는 사내 문서 원문으로 인용한다.
  - [확인] 비교 대상 제품의 기능을 실제로 확인한 뒤 표로 정리한다.
- 대상(B2B): 자동차 부품 공급사의 영업·구매 담당자, 그리고 발주하는 완성차 구매 담당자.

## 2. 데모 시나리오 소개
- 한별모터스 RFQ 한 건(가상): 전기차 워터펌프, 요청 사양은 B + 옵션 2개 조합
- 결과: EWP-12-B + 고온 옵션(OPT-HT) + 방수 옵션(OPT-IP9K), 단가 37,300원 (목표 38,000원 이내)
- 문제: 고온용 제어칩 500개 부족 → 대체칩(P-MCU-G1-ALT) 500개 추천, 추가 원가 150,000원

## 3. 전체 아키텍처 (평가항목: 아키텍처 설계)
- 그림 1 구성도: 브라우저 → Spring Boot(`/api`, `/internal`) → Agent → MCP(business, rag) → PostgreSQL + pgvector
- 그림 2 논리 구조: 화면, 업무 API, Agent 실행, 도구 계층, 저장소
- 신뢰 경계
  - 브라우저: 사용자 입력만 신뢰하지 않는다. 모든 요청은 JWT로 검증한다.
  - Spring Boot: 역할(고객/담당자)과 회사 소속을 검사한다. 내부 API는 별도 키로 보호한다.
  - Agent와 MCP: 쓰기 도구는 백엔드를 거쳐서만 실행한다.
- 저장소 구성: PostgreSQL(업무 데이터 7개 테이블, RFQ 검토 결과), pgvector(사내 문서 청크 22개)
- ISO/IEC 25010 품질 특성별 대응 [확인: 표 내용은 팀이 최종 확정]

| 품질 특성 | 설계 대응 |
| --- | --- |
| 기능 적합성 | 숫자는 코드가 계산하고 LLM은 설명 문구만 만든다 |
| 신뢰성 | 작업 상태를 DB에 저장, SSE 끊김 시 상태 조회로 복구 |
| 보안성 | JWT 역할 검사, 다른 회사 자료는 404로 숨김, 내부 API 키 분리 |
| 사용성 | 확인 필요 항목을 카드로 보여 주고 승인 전 가정을 명시 |
| 유지보수성 | 도구(MCP)와 Agent 노드를 분리, 규칙은 rules.yaml로 관리 |
| 성능 효율성 | 작업을 비동기로 실행하고 진행 상황을 SSE로 전달 |

## 4. Agent 설계 (평가항목: AI Agent 설계)
- State 구조: 요청서 원문, 추출 결과, 이슈 목록, 선정 모델과 옵션, 부품 재고, 대안, 견적, 승인 상태
- SG1 RFQ 검토: 요청서 추출 → 검증 → 담당자 확인(interrupt) → 모델·옵션 매칭 → 계약 검토 → 결과 정리
- SG2 공급·대안 분석: BOM 조회 → 가용 재고·납기 계산 → 대안 비교
- SG3 견적 작성·검증: 견적 초안 → 견적 검증
  - 검증 실패 시 재작성 루프 (재작성 한도 있음 [확인])
- SG4 승인·등록: 담당자 승인(interrupt) → 재고 재확인 → 견적 등록
  - 반려 시 SG3로 돌아가 재작성
- Agentic 요소
  - 도구 선택: 조회인지 변경인지에 따라 MCP 도구를 고른다
  - 계획: SG 단위로 다음 단계를 정한다
  - 사람 개입: 요구 확인, 승인 두 지점에서 멈춘다

## 5. MCP 설계 (평가항목: MCP 설계, 구현)
- business-mcp 9개 도구: 조회 5 · 변경 3 · 원문 1 [확인: 도구 이름 목록]
- rag-mcp: 검색 도구 + 원문 Resource (근거 문서 인용용)
- 조회와 변경 구분: 변경 도구에 destructiveHint 표시 [확인: 값 설정]
- 쓰기는 백엔드를 거친다. MCP가 DB에 직접 쓰지 않는다.
- 오류 처리: 입력 오류(VALIDATION_ERROR), 상태 충돌(409), 타임아웃 시 재시도 또는 사용자 안내

## 6. 구현과 데모 (평가항목: AI Agent 구현)
데모 순서
1. RFQ 원문 업로드
2. SSE로 진행 상황 확인 (단계 표시줄)
3. 근거와 함께 견적 표시
4. 담당자 승인 대기
5. 승인

7. 견적 등록

## 7. Harness (평가항목: Harness)
8개 구성 요소별 적용 내역 [확인: 팀이 실제 적용한 내용으로 채운다]
1. 지시문: SG별 역할과 출력 형식을 정의
2. 도구: 허용 도구 목록과 권한
3. 컨텍스트: 근거 청크만 넣는다
4. 상태·메모리: 작업 상태를 DB에 저장
5. 루프 한도: 재작성 횟수 상한
6. 가드레일: 숫자는 코드가 계산, LLM은 문구만 작성
7. 복구: 끊김 시 상태 조회, 실패 시 재시도
8. 관측: 작업 이벤트 기록, 추적 URL(trace_url)

## 8. 인증 · 대기열 처리 (평가항목: 인증 + 가산점)
- 역할: 고객(CUSTOMER)은 자기 회사 RFQ만, 담당자(MANAGER)는 전체 조회와 승인
- 인증: 로그인 후 JWT(Bearer), 만료 시간은 응답의 expires_in
- 내부 API 키: Agent가 `/internal`을 호출할 때만 쓰고 브라우저에는 전달하지 않는다
- 대기열: [확인] 작업을 큐에 넣었는지, 실패 시 재시도 방식은 무엇인지. 작업 상태 QUEUED가 있으므로 대기 단계는 존재한다.
